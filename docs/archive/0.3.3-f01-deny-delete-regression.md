Workspace: `~/Developer/Signum-Reliability`.

**Regressione riprodotta e corretta senza hardware.** Il difetto era nel cleanup
introdotto da F-01: una ACE che nega la cancellazione veniva copiata sull'oggetto
vuoto di prova e impediva di eliminarlo. L'errore reale `EACCES` veniva poi
sostituito dal codice con `EIO`. La verifica ACL rimane obbligatoria.

## Riproduzione e syscall responsabile

La riproduzione usa soltanto una directory sintetica e questa ACE:

```text
everyone deny delete
```

La ACE non è ereditabile: proteggere la directory dalla cancellazione non deve
impedire di crearvi un documento, né assegnare automaticamente quella ACE al
nuovo file.

In `sg_output_inherited_acl()` il codice copia le ACL della destinazione sulla
sottocartella vuota `.permissions`, dentro uno staging già privato, per ottenere
dal kernel le ACL che un file nuovo dovrebbe ereditare. La copia comprende anche
la ACE non ereditabile: su `.permissions` essa nega la cancellazione della
sottocartella stessa. L'acquisizione delle ACL dal file `empty` riesce; fallisce
il cleanup successivo.

Un programma diagnostico compila il sorgente C iniziale con wrapper locali di
traccia di `unlinkat` e `close`, senza alterare il codice produttivo per la
riproduzione. Risultato osservato al commit iniziale:

```text
unlinkat(empty, flags=0) => 0 errno=0
close => 0 errno=0
unlinkat(.permissions, flags=128) => -1 errno=13
close => 0 errno=0
sg_output_inherited_acl => NULL errno=5
```

`flags=128` è `AT_REMOVEDIR`. La syscall precisa è quindi
**`unlinkat(stageFD, ".permissions", AT_REMOVEDIR)`**, che restituisce
**`EACCES` (13)**. Il ramo `!clean && result` liberava le ACL appena acquisite e
impostava esplicitamente `saved = EIO` (5). L'errno 5 di questa riproduzione non
indica un errore fisico di lettura/scrittura o un difetto del token.

I test precedenti esercitavano ACE di concessione di lettura/scrittura e varianti
di ereditarietà, ma mancavano le ACE di negazione della cancellazione. I loro
esiti positivi non coprivano questa configurazione. La conclusione del precedente
rapporto F-01 va letta con questa correzione successiva.

## Correzione

Il codice produttivo modificato è soltanto:
`Sources/COutputPermissions/output_permissions.c`.
L'API e il modello dei writer Swift/C++ restano invariati.

1. Le ACL finali vengono acquisite come prima e conservate in un oggetto ACL
   indipendente in memoria.
2. Prima del cleanup vengono neutralizzate le ACL della **sottocartella vuota di
   prova** sul suo descriptor e verificato il mode privato `0700`.
3. Vengono neutralizzate anche le ACL del **file vuoto di prova** sul suo
   descriptor, con mode `0600`, prima di eliminarlo. Questo gestisce anche ACE
   deny-delete ereditate e deny-delete-child sulla sottocartella.
4. Le operazioni controllano preventivamente tipo, ownership e, per il file,
   singolo link. Cleanup e recovery usano descriptor e confronti device/inode,
   senza seguire symlink. Il recovery verifica layout noto e file effettivamente
   vuoto anche sul descriptor aperto prima di cambiare i permessi; layout
   sconosciuti e file non vuoti restano intatti.
5. In caso di fallimento si conserva il primo errno effettivo di acquisizione o
   cleanup. Una sostituzione d'identità restituisce `ESTALE`; non viene inventato
   `EIO`. Un fallimento di cleanup continua a invalidare il risultato ACL e
   impedisce di proseguire verso scrittura/pubblicazione.

### F-01 resta applicato

La directory esterna di staging rimane `0700` senza ACE; il payload del documento
resta privato durante scrittura e verifica. Le ACL vengono tolte soltanto dagli
oggetti temporanei vuoti usati per calcolare l'ereditarietà, **non dalla
cartella di destinazione né dalle ACL finali conservate in memoria**.

Le ACL finali continuano a essere applicate e rilette sul payload verificato
all'interno dello staging ancora privato, prima del rename atomico esclusivo.
Restano i controlli d'identità, di errore su write/sync/close, la validazione
pre-commit e il divieto di sovrascrittura. Nessun fallback senza ACL o errore
ignorato è stato introdotto.

Traccia della medesima riproduzione dopo la correzione:

```text
unlinkat(empty, flags=0) => 0 errno=0
close => 0 errno=0
unlinkat(.permissions, flags=128) => 0 errno=0
close => 0 errno=0
sg_output_inherited_acl => ACL errno=0
```

Una seconda esecuzione diagnostica inietta `ENOSPC` solo sul cleanup della
sottocartella: il risultato è **NULL, errno 28**, non successo e non EIO. Questo
conferma il rifiuto dell'operazione e la conservazione dell'errore reale. Non c'è
un interruttore runtime di fault nel prodotto.

## Test di regressione versionati

`Tests/SignumCoreTests/SignumFileOutputTests.swift`: **quattro nuovi metodi**,
suite writer passata da 21 a **25 test**.

- Pubblicazione Swift con deny-delete non ereditabile e con ereditarietà limitata
  alle directory, combinati con concessioni ereditabili di lettura/scrittura.
  Byte e inode pubblicati invariati, staging e payload privati, probe già rimosso
  prima della prima scrittura, ACL finali uguali al controllo creato direttamente
  dal kernel, ACL della destinazione invariate e cleanup completo.
- Acquisizione diretta delle ACL con deny-delete, deny-delete-child e loro
  combinazioni ereditabili: probe eliminato e ACL catturate conservate intatte.
- Recovery di probe abbandonato con negazioni di cancellazione; conservazione di
  layout sconosciuto e probe non vuoto, comprese le loro ACL e i loro contenuti.
- Fallimento `EEXIST` in presenza di un oggetto estraneo chiamato `.permissions`:
  errno conservato, oggetto estraneo non modificato/eliminato.

`Tools/PAdESPrototype/tests/reliability_tests.cpp`: **dieci nuovi casi**, suite
passata da 51 a **61 casi**. Comprende gli stessi controlli: due pubblicazioni di
PDF realmente firmati con chiavi software effimere, quattro combinazioni ACL sul
probe, tre scenari di recovery e il caso `EEXIST`. I PDF pubblicati passano la
verifica matematica pre-commit del writer nativo.

Nessun test hardware. I test Swift della pubblicazione usano byte sintetici;
le integrazioni CAdES esistenti verificano separatamente buste software valide,
annidate e alterate tramite le API pubbliche.

## Stato finale e limiti

**RISOLTO offline:** il percorso che restituiva EIO con deny-delete sulla
sottocartella di prova ora completa l'acquisizione ACL e la pubblicazione nei
nuovi test Swift e PAdES. Nessuna regressione osservata nelle suite complete.

**NON VERIFICATO:** nuovo collaudo reale DigitalDNA dopo questa correzione.
Non è stato toccato l'hardware né viene dichiarato ripristinato un flusso reale
che non è stato eseguito. La riproduzione sintetica identifica esattamente una
causa del messaggio segnalato, senza attestare la configurazione ACL della
cartella personale usata nel collaudo fallito.

Le restrizioni effettive della destinazione rimangono rispettate: una policy che
nega operazioni necessarie sul documento finale può ancora impedirne la
pubblicazione. Non viene rimossa per forzare il successo. Restano i limiti già
dichiarati su utenti con lo stesso UID, amministratori, filesystem supportati,
cleanup conservativo, durabilità, processi distinti, packaging e gate della Beta.
